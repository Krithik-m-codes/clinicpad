# S4 finding: ClamAV (clamd) footprint, hardening, and the clamd protocol from Node

Date: 2026-11-18. Plan 2A Task 3. Throwaway code: `spikes/s4-clamav/` (git-ignored). The EICAR string is never written to disk: the probe carries it base64-encoded and decodes it at run time.

## Verdict: GO

PING answers PONG, EICAR plain and zipped are `FOUND`, a clean PNG is `stream: OK` in well under 2 s, and peak memory (including a signature reload) is 2.0 GB, under the 3 GB gate. The strictest option set in the plan (variant 4) works, with three additions the plan did not list (see Hardening). Task 8 can use it.

## Method

`probe.mjs` talks `zPING`, `zVERSION`, `zINSTREAM` (64 KiB chunks) and `zRELOAD` over TCP. Memory: `docker stats` is too coarse (a scan lasts 20 ms), so the container's cgroup watermark `/sys/fs/cgroup/memory.peak` was read after each phase. It cannot be reset from inside the container, so each variant ran on a fresh container and the watermark was read in order: at ready, after all scans, after each reload. Scans: EICAR plain, EICAR in a stored ZIP, EICAR appended after a PNG's IEND, a clean noise PNG of 0.77 MB, 1.07 MB and 2.14 MB (5 runs each), 30 MB, 99 MB and 120 MB streams of constant bytes, and a 30-scan loop of the 2 MB PNG. Each variant then ran `zRELOAD` twice, with a scan (EICAR plus clean PNG) issued right after each reload.

## Results

### Protocol replies (identical in every working variant)

| Probe | Reply | Time |
|---|---|---|
| `zPING` | `PONG` | 3-7 ms |
| `zVERSION` | `ClamAV 1.4.6/28184/Sun Nov 15 06:27:28 2026` (format `ClamAV <version>/<daily db number>/<daily db build date>`; after a signature update and reload `ClamAV 1.4.6/28187/Wed Nov 18 06:28:39 2026`) | 3-5 ms |
| EICAR plain | `stream: Eicar-Test-Signature FOUND` | 10-12 ms |
| EICAR in a stored ZIP | `stream: Eicar-Test-Signature FOUND` | 10 ms |
| EICAR appended after PNG `IEND` | `stream: OK` (informational: not detected; the pipeline refuses trailing bytes in `inspectImage`) | 62 ms |
| clean PNG 0.77 MB | `stream: OK` | 48 ms |
| clean PNG 1.07 MB | `stream: OK` | first 63-86 ms, then 13-33 ms (median 15 ms) |
| clean PNG 2.14 MB | `stream: OK` | first 113-135 ms, then 22-51 ms (median 27 ms) |
| 30 MB constant bytes | `stream: OK` | 0.49 s |
| 99 MB constant bytes | `stream: OK` | 1.6-1.8 s |
| 120 MB constant bytes | `INSTREAM size limit exceeded. ERROR` (verbatim; clamd log line `INSTREAM: Size limit reached, (requested: 65536, max: 0)`); the connection closes and a following `zPING` answers `PONG` | 0.85-1.1 s |
| 30 sequential 2 MB scans | all OK | 0.73 s for 20 scans, about 36 ms each |

The reply carries a trailing NUL with the `z` prefix commands; strip it before matching. Two distinct non-OK shapes exist and the adapter must treat both as not clean: `stream: <name> FOUND` and `<text> ERROR` (no `stream:` prefix on the size-limit error).

### clamd limits (`clamconf` in the image)

`StreamMaxLength = 104857600` (100 MiB, so the app's cap, 10 MB or lower, is far below it), `StreamMaxPort 2048`, `MaxThreads 10`, `MaxQueue 100`, `ReadTimeout 120` s, `CommandReadTimeout 30` s, `SelfCheck 600`, `ConcurrentDatabaseReload yes`, `MaxFileSize`/`PCREMaxFileSize` 104857600, `MaxScanSize` 419430400, global scan time limit 120000 ms (log). The 120 MB probe confirms the stream limit. The adapter should still use its own short deadline (plan: one shared deadline for VERSION and INSTREAM) because clamd waits up to 120 s on a stalled stream.

### Start-up

| Case | Time until `PING` answers `PONG` (poll interval 3 s, so +-3 s) |
|---|---|
| Fresh container, image's own signatures, freshclamd running | 19.7 s (log: clamd loaded 3.6 M signatures at +19 s) |
| Hardened variants, fresh named volume (first start, volume filled from the image) | 16.3-16.5 s |
| Warm start, `--network none`, volume already updated | 14.9 s (to PONG via `clamdscan --ping`) |

There is no multi-minute first download: the signatures ship in the image. The plan's "first start takes minutes" does not apply to this tag. Allow `CLAMAV_START_SECONDS=20` (warm), health start period 120 s as a margin for slower disks. `docker compose` healthcheck `clamdcheck.sh` reported `healthy`.

### Memory

| Phase (3 g limit unless stated) | cgroup `memory.peak` (watermark) | Notes |
|---|---|---|
| Idle, database loaded | `memory.current` 1.0-1.1 GB (anon 0.99 GB, file cache 0.14-0.17 GB); `docker stats` 1.011 GiB | clamd RSS 953-976 MB |
| Start-up watermark | 1.0 GB (no freshclamd) / 1.56-1.70 GB (with freshclamd and its database test) | |
| After 5 + 5 clean scans, 30 / 99 / 120 MB streams, 30-scan loop | unchanged (1.0-1.2 GB) | scanning does not raise memory measurably |
| **During `zRELOAD`** | **1.99 GB (variants 4), 2.08 GB (variant 3), 2.17 GB (variant 2), 2.14-2.17 GB (default)** | clamd builds the new engine beside the old one (`ConcurrentDatabaseReload yes`), so anon memory doubles for about 15 s (log: reload 13:19:02 to 13:19:17) |
| Second reload | same watermark as the first | no growth |

The reload peak is the number that sizes the limit, not the scan. With `CLAMAV_NO_FRESHCLAMD=true`, variant 4 ran correctly under `--memory 2g` (peak 1.99 GB = 1.85 GiB, OOMKilled false, 0 restarts, two reloads) and under 2500m. A 2 g limit leaves only about 7 % headroom, and `daily` grows over time, so the recommendation is 2.5 g. Disabling concurrent reload (`ConcurrentDatabaseReload no`) would halve the reload peak but needs a writable `/etc/clamav/clamd.conf` (the image's `CLAMD_CONF_*` env handling uses `sed -i`, which fails with a read-only root); a mounted config file would be required. Not needed at 2.5 g, so not adopted.

A scan keeps working during a reload: an EICAR stream and a clean PNG issued right after `RELOADING` answered `FOUND` and `OK`. After the reload, `zVERSION` shows the new database (about 15 s later).

### Hardening variants

| # | Options (all with `--security-opt no-new-privileges:true`) | Result |
|---|---|---|
| 1 | `--cap-drop ALL` | Fails: `install: can't change ownership of /run/clamav: Operation not permitted` |
| 2a | `--cap-drop ALL --cap-add CHOWN --cap-add SETUID --cap-add SETGID --cap-add DAC_OVERRIDE` (the plan's list) | Fails: `install: can't change permissions of /run/clamav` (needs `FOWNER`) |
| 2 | variant 2a plus `--cap-add FOWNER` | Works. PONG at 19.6 s |
| 3a | variant 2 plus `--read-only --tmpfs /tmp --tmpfs /run/clamav -v <vol>:/var/lib/clamav` (the plan's list) | Fails: `ln: /var/lock/lock: Read-only file system` (`/var/lock` links to `/run/lock`) |
| 3b | with `--tmpfs /run` instead | Hangs forever "Socket for clamd not found": `Failed to open log file /var/log/clamav/clamd.log: Read-only file system` |
| 3 | variant 2 plus `--read-only --tmpfs /tmp --tmpfs /run --tmpfs /var/log/clamav:uid=100,gid=101 -v <vol>:/var/lib/clamav` | Works. PONG at 16.4 s |
| 4 | variant 3 plus `-e CLAMAV_NO_FRESHCLAMD=true` | Works. PONG at 16.5 s. All probes as above; **strictest working set** |

Strictest working set (`CLAMAV_OPTIONS`), compose form:

```yaml
cap_drop: [ALL]
cap_add: [CHOWN, SETUID, SETGID, DAC_OVERRIDE, FOWNER]
security_opt: ["no-new-privileges:true"]
read_only: true
tmpfs: ["/tmp", "/run", "/var/log/clamav:uid=100,gid=101"]
volumes: ["clamav_db:/var/lib/clamav"]
environment: ["CLAMAV_NO_FRESHCLAMD=true"]
mem_limit: 2500m
```

The init script runs as root, so the five capabilities cannot be dropped further without a different entrypoint (`/init-unprivileged` and `--user 100:101` were not tried). `pids` stayed at 4-5. The image's `/init` does `chown -R clamav:clamav /var/lib/clamav`, so the database volume cannot be mounted `:ro` into the scan container.

## How signatures arrive, and scans without network

Signatures need network at least once, but not on this image: `main.cvd`, `daily.cld` and `bytecode.cvd` are already in it, so a scan container never needs egress to start. Updates are a separate job:

1. **Update container (has egress, no ports):** same image, `--entrypoint freshclam` with `--foreground --stdout --user=clamav --checks=1`, the same cap set (read-only root, `--tmpfs /tmp`, `--tmpfs /var/log/clamav:uid=100,gid=101`), the same named volume mounted at `/var/lib/clamav`. Measured: 6.9 s to fetch `daily` 28184 -> 28187 and write it to the volume (it prints `Clamd was NOT notified`, expected). Run it from a scheduler (the cadence was not measured; the official mirror may rate-limit frequent checks, so a few runs per day is the sensible range).
2. **Scan container (no egress):** `CLAMAV_NO_FRESHCLAMD=true`, same volume. After an update the job sends `zRELOAD` to clamd (about 15 s, scans keep working, peak 2.0 GB, see Memory); or restarts the container (about 16 s).
3. **Local development and CI:** CI starts the service with `CLAMAV_NO_FRESHCLAMD=true` (uses the image's baked-in signatures, no network, deterministic); the smoke test only needs EICAR detection, which is in the baked-in `daily`/`main`. A developer machine can run the same compose service without any update job; signatures then age with the image tag, which is fine for tests.

What was proven on this machine:

- With `--network none` the container has only `lo`, started and reached PONG in 14.9 s, `clamdscan` scanned a file inside it (`OK`), and `wget` to the internet failed. So clamd itself needs no network after start.
- With `docker network create --internal` the container has no route out (`Network unreachable`), and a peer container on that network reached clamd on 3310 (`PONG`). But Docker does not publish ports of containers on an internal network: the host `127.0.0.1:3311` was `ECONNREFUSED`.
- So on a developer machine where Next runs on the host, the clamav service must sit on a normal bridge with `127.0.0.1:3310` published. Its egress is then not blocked by Docker, but with `CLAMAV_NO_FRESHCLAMD=true` clamd opens no outbound connection (observed: none; only the update container uses the network). True egress blocking holds only where the app runs in a container on the same internal network (production), or via a host or cloud firewall. This is an ops item for Q4 (hosting) and is recorded as such, not solved here.

## Decision

**GO.** Values for Task 8:

- `CLAMAV_IMAGE=clamav/clamav:1.4.6@sha256:4cc4350d3fded380caf1799e76c0d1c93f3fa40af99c0cb2862ec0c9b117718a`
- `CLAMAV_OPTIONS=` the compose block above (`cap_drop ALL` + `CHOWN SETUID SETGID DAC_OVERRIDE FOWNER`, `no-new-privileges`, read-only root, tmpfs `/tmp`, `/run`, `/var/log/clamav:uid=100,gid=101`, named volume at `/var/lib/clamav`, `CLAMAV_NO_FRESHCLAMD=true`)
- `CLAMAV_MEM_LIMIT=2500m` (peak 1.99 GB during a concurrent signature reload; peak rounded up to the next 0.5 GB is 2.0 GB, raised one step for growth of the `daily` database; scans and idle stay near 1.0 GB). Do not go below 2g.
- `CLAMAV_START_SECONDS=20` (measured 15-20 s); compose healthcheck `start_period` 120 s.
- Over-size reply (not expected from the app's own caps): `INSTREAM size limit exceeded. ERROR`; server `StreamMaxLength` is 104,857,600 bytes.
- Adapter rules from the measurements: strip the trailing NUL; accept only `stream: OK` as clean; `FOUND` and any `ERROR` or timeout are refusals (fail closed); send `INSTREAM` chunks of at most 64 KiB; use one shared deadline; the p50 latency to budget is 15 ms (1 MB) and 27 ms (2 MB), the first scan after start 60-130 ms, so a 5 s deadline is generous.
- Task 8 smoke test: EICAR decoded at run time (never committed), `VERSION` matches `/^ClamAV \d+\.\d+\.\d+\/\d+\//`.
- A reload scheduled while uploads are in flight is safe (scans answered during it); the memory limit must stay at or above 2.0 GB for that reason.
